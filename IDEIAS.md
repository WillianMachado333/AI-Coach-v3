## Adaptação ao aprendiz (Eric-2026-08-10)

Três features estruturais que Eric pediu na call do dia 10 e que redefinem o que a Erica faz de forma pesada. Não são polish — são novas capacidades. Cada uma precisa promoção explícita antes de virar AFAZERES.

- **[📋] Learning-style detection + adaptação (Eric-2026-08-10)** — Eric: *"I think you're an exploratory learner… just be careful that we don't gear the coach for an exploratory learner. The AI coach needs to work out the learning style and use that."* Oito estilos com pesos indicativos: **prático 25%**, **estruturado 20%**, **exploratório 17%**, **colaborativo 15%**, **reflexivo 13%**, **independente 10%**, **conceitual** e **observacional**. Prático + estruturado juntos = ~45% — a maioria NÃO é exploratória. Erica precisa (a) detectar estilo a partir de sinais no diálogo (padrões de resposta, tipo de pergunta, o que o usuário pula), (b) manter uma estimativa persistente (associa ao Persistent Memory / user profile no vector store), (c) ajustar formato (prático = "faz isso na segunda", estruturado = passos numerados, exploratório = perguntas abertas, colaborativo = "vamos pensar juntos"). Não pode calibrar experiência default no estilo do construtor (Willian ou Eric). Custo: L (detecção + persistência + N variantes de tom). Depende de Persistent Memory.
- **[📋] Scaffolding diagnosis — coach raciocina sobre pré-requisitos (Eric-2026-08-10)** — Eric: *"Part of a coach's role is to work out which of the bits of scaffolding is missing… we're having an issue that you seem to lack courage and that might be because you're missing some of the self-awareness stuff."* Coach não deve só responder o que está na frente — deve considerar o que falta N-2 escadas atrás. Requer (a) modelo de dependências entre competências (grafo: courage ← self-awareness ← naming emotions), (b) prompt tuning que diz "quando o usuário demonstra dificuldade em X, considere prerequisites Y e Z antes de dar tática pra X", (c) recall persistente de dificuldades vistas antes. Custo: L. Depende de Persistent Memory + framework populated (frameworks são o grafo de scaffolding). Grande valor porque diferencia coach de FAQ.
- **[📋] User-declared preferences vs config (Eric-2026-08-10)** — Eric: *"Some things about preferences, not so much as a configuration, but do you like long or short answers?"* Distinto de configuração admin — é preferência que o próprio usuário declara e Erica respeita. Exemplos: comprimento de resposta, quer histórico vs quer só ação, quer visualização vs texto, quer voz ou texto por default. Overlap parcial com CP-02 (communication style toggle) mas mais amplo — CP-02 é sobre "estilo emocional" (calm/direct/etc); user prefs é sobre formato/mecânica de interação. Requer (a) UI leve pro usuário declarar (uma linha na primeira sessão + toggle disponível a qualquer momento), (b) persistência por usuário (Persistent Memory), (c) prompt injection dessas prefs em cada boot. Custo: M. Depende de Persistent Memory.
- **[💡] Explicit user-declared context — open question (Eric-2026-08-10)** — Eric perguntou: *"What I didn't see here is this idea of context. So when someone comes in, how would we say, this is my context."* Resposta na call foi activity log + page context + goals — mas tudo isso é **inferido**. Ele quer forma deliberada do usuário **declarar** o próprio contexto. Não resolvido no design. Precisa (a) forma leve do usuário abrir *"contexto: estou pensando em mudar de emprego, tenho 2 filhos, X anos de carreira"* sem virar questionário chato, (b) integração com Persistent Memory pra persistir, (c) usar sem violar preferência "não repetir o que já contei". **Bloqueado por decisão de UX** — pode ser primeira pergunta na sessão de retorno, pode ser botão "atualize meu contexto", pode ser "context tags" tipo mood emoji. Discussão antes de scopear.

- **[🔨] Iframe flutuante em vez de lightbox Wix** — arquitetura já mapeada em [ai-coach-floating-iframe-architecture]. Permite persistência entre navegações, pré-warm, integração DOM-level.

## Relação de longo prazo — memória, metas, continuidade (Eric-2026-08-09)

Todo este bloco vem do doc `AI Coaching Experience and Resource Support Requirements (ES draft) 9-Aug-2026.docx` (Eric). Tese central: o AI Coach deveria se comportar como **coach contínuo**, não como chatbot de perguntas isoladas. Eric marca este bloco inteiro como **Phase 1 / Priority 1** — antes de qualquer outra expansão. Nada disso existe hoje.

- **[📋] Onboarding conversacional experimentável (ON-01 → ON-04)** — primeira sessão como conversa, não questionário. Progressive discovery — uma pergunta relevante por vez, coach explica o "por quê" quando apropriado, usa respostas anteriores pra decidir a próxima, nunca repete algo já respondido. Onboarding tratado como área com **experimentação estruturada**: variáveis a testar (opening question, N perguntas antes de valor, empatia, timing da primeira ação sugerida, comm-style, whether "why this question" é dito). Métricas específicas: first-session completion, conversation length, meaningful responses, return rate, % users com goal formado, % agreeing to action, return rate após action. Requer infra de variantes por seed/tag no simulador e produção. Doc: ON-01 a ON-04.
- **[📋] Structured Goal + Action capture (GA-01 → GA-03)** — quando meta emerge naturalmente, sistema captura em forma estruturada: `goal`, `description/context`, `date`, `status`, `motivation`, `known_obstacles`, `desired_outcome`. Ação identificada como "próximo passo realista" (praticar comportamento, ter conversa, ler artigo, fazer quiz, completar parte de curso). Commitment confirmado em linguagem leve — Eric explicitamente pede pra **evitar** linguagem formal tipo "commit". Exemplo: *"Antes da gente conversar de novo, você quer contribuir com pelo menos uma ideia na próxima reunião do seu time — soa realista?"*. Requer: (a) schema persistente, (b) prompt tuning pra Erica reconhecer o momento e não forçar goal-statement antes do usuário estar pronto, (c) painel no admin/co-worker das metas ativas por usuário. Depende de Persistent Memory abaixo. Doc: GA-01 a GA-03.
- **[📋] Persistent Coaching Memory cross-session (CC-02)** — **este é o item mais estruturalmente novo**: Erica lembra da conversa anterior quando o usuário volta. Retém goals, actions, progress, challenges, resource preferences, coach preferences, contexto que o usuário compartilhou. Requer: (a) schema persistente por usuário (hoje `/data/sessions` é append-only por sessão, sem consolidação por user); (b) mecanismo de write no fim de sessão (ver End-of-conversation summary abaixo); (c) read no boot que injeta memória relevante em `Injected Data` do AFAZERES #3; (d) **política de privacidade + controles de edição/deleção** — Eric explicitamente pede "separate privacy and technical requirements"; (e) reconciliação quando conversa evolui ("essa meta ainda importa?"). Eric marca **Priority 1 / Phase 1**. Doc: CC-02. **Atualização Eric-2026-08-10:** confirmou de novo — proposta Willian de "user profile no vector store, coach gera insights e salva" foi respondida com *"completely agree"*. Torna Persistent Memory precondition pra Learning-style detection, Scaffolding diagnosis, User-declared preferences e Explicit user context — a maioria das capacidades novas dessa call depende deste item. Muito boa candidata a próxima promoção grande.
- **[📋] End-of-conversation summary + capture (CC-01)** — ao detectar fim de conversa significativa (silêncio prolongado, close explícito, longa pausa), sistema extrai e persiste: current goal, insight/issue discutido, ação combinada, próximo passo, recursos sugeridos, follow-up pendente. Nem toda conversa contém todos os campos. Requer heurística ou LLM pass no evento de fim. Depende de Persistent Memory acima. Doc: CC-01.
- **[📋] Resume Previous Conversation (CC-03)** — usuário retorna, Erica abre citando previamente: *"Da última vez você queria contribuir com uma ideia na reunião do time — como foi?"*. Wording varia naturalmente. **NÃO** pressupõe que a meta anterior ainda importa; permite mudar direção. Depende de Persistent Memory + End-of-conversation summary. Doc: CC-03.
- **[💡] Progress reflection periódica (CC-04)** — em conversas de retorno, Erica ajuda a refletir: "O que mudou? O que funcionou? Ainda importa essa meta? Precisamos mudar a ação?". Precisa timing (não em toda conversa, só quando há algo pra refletir). Depende de Persistent Memory + histórico de actions. Doc: CC-04.

## Voz / Realtime

- **[⚠️] Barge-in robusto** — hoje funciona segundo Willian testou, mas VAD threshold=0.95 e handler sem `response.cancel` explícito. Se voltar a falhar, root cause já mapeado em [ai-coach-voice-barge-in-broken].
- **[💡] Detectar silêncio prolongado → pergunta suave** — se user parou de falar por N segundos sem intenção clara, coach faz uma pergunta gentil ao invés de esperar.
- **[🐛] Ícone em animação falante o tempo todo no modo voz** — ao entrar no modo voz, o ícone da Erica fica em animação "ela-está-falando" permanentemente, mesmo quando ela está em silêncio (escutando o usuário, esperando, ou entre turnos). Deveria animar SÓ enquanto áudio da Erica está sendo emitido. Impacto: cue visual perde sentido — pra usuário parece que ela ficou congelada num loop de fala. Conflita diretamente com a intenção descrita em [[ai-coach-voice-natural-by-default]] (animação = "ela está falando"). Hipótese: state machine no bridge/app.js entra em `speaking` no `session.updated` e não sai; ou não escuta `response.audio.done` / `output_audio_buffer.stopped`. Investigar handlers de eventos Realtime em `app.js` e classes CSS aplicadas no ícone.
- **[💡] Karaoke highlight — sublinhar palavra que a Erica está falando agora** — Willian viu no WhatsApp: quando transcreve um áudio, a UI destaca a palavra atual em sync com o playback, o usuário lê e ouve ao mesmo tempo. Replicar aqui: enquanto Erica fala, a palavra correspondente no balão de texto ganha highlight (background sutil ou peso/cor). Valor: (a) acessibilidade — usuário lê no ritmo dela sem precisar decidir "leio ou ouço?", (b) confia mais no coach quando vê que texto e áudio batem, (c) fica óbvio onde pausar/pular. Implementação: Realtime API já emite `response.audio_transcript.delta` token-a-token quase em sync com `response.audio.delta`; guardar timestamp de cada delta no client e casar com `AudioContext.currentTime` do playback pra descobrir a posição atual. Complicação: TTS pode adiantar/atrasar em relação ao transcript — precisar tolerância ±150ms. Não bloquear nada se o sync falhar, degrada pra "texto sem highlight".
